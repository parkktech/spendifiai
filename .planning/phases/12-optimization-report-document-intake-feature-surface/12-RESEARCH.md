## Summary

Phase 12 connects three production sub-systems for the first time. The P10 rules engine (TaxRulesEngineService → OptimizationFinding) and P11 interview/narration machinery (NarrationService, UserTaxFact, DurableFactsController) are fully shipped. Phase 12 assembles their outputs into a user-visible ranked report, extends the v2.0 vault document pipeline with six new financial document types plus substantiation doc categories, wires extracted facts through the D4 proposal/confirm gate into UserTaxFact, and builds the two new Inertia pages (Optimize My Income, User/Family Profile) plus nav entries.

The key implementation insight is that `ExtractTaxDocument` job currently fires NO event on completion — the staleness wiring between document extraction and report generation is entirely missing and must be added as P12 wave 0. Similarly, no code path today creates `UserTaxFact` proposals from extracted document fields; the `DurableFactsController` confirm/supersede endpoints exist and are correct, but the proposal-creation side must be built.

All three new Claude call sites in this phase (report section narration, pay-stub fact description, benefits-guide fact description) must mirror the NarrationService security contract exactly: estimated_value_cents excluded from payload, SAFE-01 system prompt, 256-token max per finding narration.

**Primary recommendation:** Build in strict wave order — migration + events first (wave 0), then enum cases + extraction schemas + assembler extension (wave 1), then report generator service + job (wave 2), then PDF export + proposals bridge (wave 3), then frontend pages (wave 4). Attempting frontend before the report API exists will block.

## Implementation Detail: 3rd Claude Call Site (Report Narration)

### OptimizationReportNarratorService pattern

Mirrors `NarrationService` exactly. Key contract differences for reports:

```php
// Section-level narration (called once per section, not per finding)
// Sends: section_title, finding_summaries[] (finding_type, severity, band, legal_basis)
// Explicitly EXCLUDES: estimated_value_cents, net_cash_cost, tax_saved, cliff_bonus_value
// Output: 2-4 sentences of section overview prose

const SYSTEM_PROMPT = <<<'SYS'
You are an educational financial assistant. Write a brief overview of the following
tax optimization findings for a user-facing report section.

RULES (non-negotiable):
1. Use "may", "could", "consider", "might", "worth exploring" language — always educational.
2. NEVER state dollar amounts. Use "potentially meaningful" or "worth reviewing" instead.
3. NEVER say "you qualify", "you owe", "you are entitled", "you should".
4. NEVER give filing-status or securities-transaction advice.
5. Write 2-4 sentences of plain English overview for a non-expert reader.
6. End with: "Consider discussing these items with a tax professional."

OUTPUT: Return ONLY the 2-4 sentence overview. No JSON. No markdown. No bullets.
SYS;
```

The payload to Claude is:
```json
{
  "section_title": "Retirement Contributions",
  "findings": [
    { "finding_type": "ira_headroom", "severity": "medium", "band": "conditional",
      "legal_basis": "IRC §219; Rev. Proc. 2025-32 IRA limits" }
  ]
}
```

`estimated_value_cents` is deliberately excluded (SAFE-03 grep-gate test covers this).

```php
        'label' => 'Employer has 401(k) plan', 'volatility' => 'stable'],
    'employer_match_formula'         => ['fact_key' => 'employer.match_formula',
        'label' => 'Employer match formula', 'volatility' => 'stable'],
    'after_tax_401k_available'       => ['fact_key' => 'employer.after_tax_401k_available',
        'label' => 'After-tax 401(k) available (mega backdoor gate)', 'volatility' => 'stable'],
    'hdhp_hsa_available'             => ['fact_key' => 'employer.hdhp_hsa_available',
        'label' => 'HDHP/HSA plan available', 'volatility' => 'stable'],
    // ... other benefits fields
];

public function proposeFacts(TaxDocument $document): int
{
    // CRITICAL: source_type MUST be 'document_extraction' — UserTaxFact::recordFact()
    // will write is_current=false (a proposal). Never silently overwrites user-entered values.
    $map = match ($document->category) {
        TaxDocumentCategory::PayStub => self::PAYSTUB_FACT_MAP,
        TaxDocumentCategory::BenefitsGuide => self::BENEFITS_FACT_MAP,
        default => [],
    };
    $fields = $document->extracted_data['fields'] ?? [];
    $count = 0;
    foreach ($map as $fieldName => $factConfig) {
        $fieldData = $fields[$fieldName] ?? null;
        if ($fieldData === null) continue;
        $value = $fieldData['value'] ?? null;
        $confidence = (float) ($fieldData['confidence'] ?? 0.5);
        if ($value === null || $value === '') continue;
        // Store confidence in metadata (non-PII) for per-field UI display
        UserTaxFact::recordFact(
            userId: $document->user_id,
            factKey: $factConfig['fact_key'],
            value: (string) $value,
            sourceType: 'document_extraction',
            label: $factConfig['label'],
            volatility: $factConfig['volatility'],
            taxYear: $document->tax_year,
            sourceId: (string) $document->id,
            metadata: ['confidence' => $confidence, 'document_id' => $document->id],
        );
        $count++;
    }
    return $count;
}
```

The `$hidden = ['value']` on UserTaxFact ensures the encrypted value never reaches the API response. The `metadata` column (JSONB, non-PII) carries `confidence` for per-field UI display on the proposal card.

## Common Pitfalls

### Pitfall 1: Writing to `estimated_value_cents` in the report generator

**What goes wrong:** The SAFE-03 grep-gate test (`tests/Unit/EstimatedValueGuardTest.php`) scans all PHP files in `app/` and fails the build if any file other than `TaxRulesEngineService.php` assigns `estimated_value_cents`. Report generation reads this value for ranking but must never write it.

**How to avoid:** In `OptimizationReportGeneratorService`, read `$finding->estimated_value_cents` for sorting. Never assign it. The narration payload must not contain any monetary column.

**Warning signs:** Build fails with `SAFE-03: estimated_value_cents only assigned in TaxRulesEngineService`.

### Pitfall 2: `extracted_data` field structure — nested vs flat

**What goes wrong:** `TaxDocumentExtractorService::extract()` returns `{ "fields": { "field_name": { "value": "...", "confidence": 0.9 } }, "overall_confidence": 0.87 }` and this is stored as `extracted_data` on the TaxDocument. But some callers in the existing `sumFromDocuments()` switch read `$data['wages']` (flat) rather than `$data['fields']['wages']['value']` — the code is inconsistent because older arms were written before the field-with-confidence schema solidified.

**How to avoid:** For all NEW P12 code (PaystubFactExtractorService, new sumFromDocuments arms), always read `$data['fields'][$fieldName]['value'] ?? null`. Do not copy the inconsistent existing pattern.

**Warning signs:** Fields silently return null even when the document has the data.

### Pitfall 3: `UserTaxFact::recordFact()` called outside `document_extraction` for new doc types

**What goes wrong:** If `ExtractProfileFacts` job uses `source_type = 'interview_answer'` instead of `'document_extraction'`, the fact immediately becomes `is_current=true`, silently overwriting user-entered values and bypassing the D4 confirm gate. This violates the locked owner Decision 4 and the DurableFactsController::confirm() guard.

**How to avoid:** Always pass `sourceType: 'document_extraction'` when creating proposals from extracted documents. The `recordFact()` method checks this and sets `is_current=false` for proposals.

**Warning signs:** Proposals appear in the "confirmed" list (not "proposals") in `GET /api/v1/optimizer/facts` response.

### Pitfall 4: Thundering-herd from interview staleness

**What goes wrong:** The interview has 20+ questions. If `UserAnsweredQuestion` listener dispatches `GenerateOptimizationReport` on every answer, a user completing the interview queues 20+ report generation jobs, each making Claude API calls.

**How to avoid:** `GenerateOptimizationReport implements ShouldBeUnique` with `uniqueId()` returning `"{$this->userId}:{$this->taxYear}"`. Use `->delay(now()->addSeconds(30))` on dispatch. Only one job runs; the rest are dropped.

**Warning signs:** Redis queue fills with duplicate report generation jobs; Anthropic API rate limit errors.

### Pitfall 5: dompdf memory exhaustion on long reports

**What goes wrong:** Default PHP memory limit is 128M. A report with 20+ findings, each with 3-sentence narrations, plus the glossary section (RPT-07), easily hits this limit.

**How to avoid:** Add `ini_set('memory_limit', '512M')` at the start of the report generation job's `handle()` method, before `Pdf::loadView()`. Keep the Blade template simple — no nested loops over large collections; flatten the data array before passing to `loadView()`.

**Warning signs:** `PHP Fatal error: Allowed memory size exhausted` in queue worker logs.

### Pitfall 6: `/profile` route collision with Breeze

**What goes wrong:** `web.php` already has `Route::get('/profile', ...)` for Breeze's profile edit page (name: `profile.edit`). Adding a new `/profile` route for "User/Family Profile" creates a routing conflict.

**How to avoid:** Use `/user-profile` as the path and `user-profile` as the route name. Both are unused.

**Warning signs:** `Route [profile] already defined` error, or Breeze password-change redirects break.

### Pitfall 7: Fact proposals for BenefitsGuide boolean fields

**What goes wrong:** BenefitsGuide boolean fields (`has_401k`, `after_tax_401k_available`, etc.) come back from Claude as `"true"` or `"false"` strings. If stored directly in UserTaxFact as a string and later compared with `=== true`, the comparison fails.

**How to avoid:** Store boolean fields as the string `"yes"` or `"no"` in UserTaxFact (consistent with existing interview answer convention). The `metadata` field can carry the original boolean for UI display. Document this convention in `PaystubFactExtractorService` code comments.

### Pitfall 8: Report stale_since null when report has never been built

**What goes wrong:** A new user who has just answered interview questions may have 10 OptimizationFindings but no OptimizationReport row yet. If the staleness check reads `$report->is_stale` and $report is null, a null pointer exception occurs.

**How to avoid:** In the report controller, use `OptimizationReport::firstOrCreate(['user_id' => $userId, 'tax_year' => $year], ['is_stale' => true, 'sections' => []])`. Callers always get a model instance. If `is_stale === true` and `sections` is empty, trigger report generation and return a "generating" state to the UI.
