**D1. TaxRulesEngineService gains a validator that suppresses expired rules, surfaces stale `last_verified`, and enforces `band` before any finding renders. Seed the sunset calendar: tips/OT/senior/auto-loan 2028; SALT 2029; QOF end-2026; enhanced ACA credits already expired; residential energy credits expired 2025 (amendment scanner only). `band=suppress/hard_block` is the mechanism Phase 13's SAFE-06 list plugs into. Retrofitting effective dating later is expensive — this ships in wave 11a.

**D2. Materiality gates and band cutpoints live in config, never in service code (FLAG-08).** Either `config/tax-rules.php` or a `config/tax-detection.php` sibling. $100 single-txn floor (unless recurring), $500/yr recurring gate, $1,000 single-txn interrogate, address-matched and loan-servicer transactions always interrogated. Note the 10-03 precedent distinction: CrossSourceReviewService tolerances were deliberately class constants because they are business logic, not IRS-updated values; materiality gates and band cutpoints follow the spec (config) because the spec explicitly demands it — document the distinction in the plan.

**D3. Durable-facts store per the locked storage design (STORE-01/02), ANCHORED to the Enhanced Tax Profile (LOCKED owner Decision 1).** The store EXTENDS the existing Enhanced Tax Profile system (`UserFinancialProfile` + `EnhancedProfileSection.tsx` on `Settings/Index.tsx`) — it is NOT a disconnected parallel store. Three new tables, all strictly additive:
- `user_tax_facts`: append-only ask-once graph. Non-sensitive queryable keys (`fact_key` namespaced, e.g. `ira.pretax_balance_range`, `employer.match_pct`, `method.mileage`), ENCRYPTED `value` (TEXT, `'encrypted'` cast, $hidden; money = integer-cents-as-string), `volatility` (permanent | stable w/ `reconfirm_after` | annual w/ `tax_year`), provenance (`source_type` interview_answer|document_extraction|detector|profile_field|user_edit + `source_id` + `asserted_at`/`confirmed_at`), supersession (`is_current` + `superseded_by_id`; rows never updated-in-value or deleted). Postgres partial unique index on (user_id, fact_key, coalesce(entity_id,0), coalesce(tax_year,0)) WHERE is_current. Never index or query the encrypted value column; never put PII in fact_key/label.
- `tax_profile_entities`: vehicles / properties / business entities (`entity_type`, user-facing `label`, ENCRYPTED `attributes` JSON incl. the property basis ledger entries, each referencing its Vault receipt by tax_document_id). People are NOT duplicated — Dependent/Household models already exist.
- `interview_sessions`: persisted state machine (queue/asked keys as plain jsonb of fact_keys; ENCRYPTED `assertions` transcript; partial unique one in-progress session per user-year). Answers write THROUGH to UserTaxFact; the session keeps the ordered Q/A transcript for provenance.
Anchoring mechanics (Decision 1): existing profile checkbox/field values seed facts with `source_type=profile_field`; every learned fact (interview- or document-sourced) surfaces in the user's Settings for review/correction via an ADDITIVE UI hook — a learned-facts review list rendered alongside `EnhancedProfileSection` (additive columns/models + additive UI section only; no changes to existing fields' API shape or existing `EnhancedProfileSection` behavior; the fuller "User/Family Profile" surface is P12 per owner Decision 5).
Retirement multi-account representation (LOCKED owner Decision 2 — correctness requirement): retirement facts model SIMULTANEOUS account types (Roth IRA + Traditional IRA + employer 401(k) types) with per-type contribution amounts where known; the legacy single `ira_type` column stays untouched (existing API). Because the IRA annual limit is SHARED across Roth+Traditional ($7,500 for 2026, +$1,100 catch-up), TaxRulesEngineService IRA-headroom inputs MUST consume combined Roth+Traditional contributions — never just a type label.
Confirmation gate (LOCKED owner Decision 4): facts with `source_type=document_extraction` are written as PROPOSALS (not `is_current`) carrying per-field extraction confidence; they never feed skip-logic, headroom math, or findings until the USER CONFIRMS (confirmation flips them current and sets `confirmed_at`); they NEVER silently supersede `user_edit`/`interview_answer`/`profile_field` facts. Confirmed-from-document facts count as answered for interview skip-logic. (The document-intake side itself is P12/DOC-07; P11 builds the proposal/confirmation states so P12 plugs in without schema rework.)
Carry-forward: permanent facts never re-asked; stable facts get a one-tap "still true?" re-confirmation after `config('tax-rules.facts.reconfirm_months', 12)`; annual facts expire with the tax year and should mostly be DERIVED not asked. `IncomeOptimizationProfile::answerableFields()` is extended (additive method change) to consult UserTaxFact so the CTX-04 skip gate covers durable facts + snapshot + UserFinancialProfile in one place. FACT-CHECK FIX baked in: IncomeOptimizerDataAssemblerService::readProfileFlags currently omits `business_type` and `housing_status` — extend it additively so entity/housing gates can read them. Every new model: scopeForUser(), Policy (user->id === resource->user_id), cascadeOnDelete for GDPR deleteAccount().
